# `editor/` — Editor Experience Review & Roadmap

Scope: the `editor/` directory (High-Energy's `aux/` until 2026-10-22) is Heimdall's home for VS Code-side tooling that makes
high-energy-physics (HEP) work less painful. Today it ships two extensions; this report
audits them, proposes the next round of work, and lays out a concrete plan for a
HEP-focused icon theme derived from Material Icon Theme.

---

## 1. Current state

```
editor/
├── cmnd-syntax/          # syntax highlighting for Pythia8 .cmnd files
└── hep-contrast-theme/   # high-contrast light VS Code color theme
```

### 1.1 `cmnd-syntax` — audit

**What it does.** Registers a `cmnd` language and gives `.cmnd` files four-token
highlighting: comments (`!…`), and the `Namespace:Key = Value` triple plus the `=`.

**Strengths.**
- Tiny surface area, easy to maintain.
- The four-token split is the *right* mental model for Pythia commands.
- VSIX already built and installable (`cmnd-syntax-0.0.1.vsix`).

**Weaknesses.**
- **Value type is flat.** Every RHS is `string.unquoted.cmnd` — so `on`, `off`,
  `1.5e-3`, `13000`, `proton`, and `2212` all paint identically. Real Pythia cards
  mix booleans, ints, floats, particle IDs, and free strings; collapsing them is
  a missed opportunity.
- **No structure tokens.** Pythia cards routinely use `Main:numberOfEvents`,
  `Beams:eCM`, `PDF:pSet`, `HardQCD:all`, etc. The first segment is effectively
  a category — worth its own scope so themes can dim or boost it.
- **No commented-out commands.** `! Main:numberOfEvents = 1000` is by far the most
  common pattern in real cards; right now the leading `!` swallows the whole line
  as a comment, which is correct, but there's no `comment.line.directive` scope so
  you can't theme "disabled command" distinctly from "prose comment".
- **Doesn't recognise the `=` form variants.** `:=` doesn't appear in Pythia,
  but `Print:quiet = on` vs `Print:quiet=on` (no spaces) is allowed — current
  regex requires spaces around `=`.
- **No injections for `.cmnd`-in-string blocks.** When `.cmnd` snippets appear
  inside C++ string literals (which they do in `_Lambda_Reconstruction.cc` and
  the `dump/examples/*.cc` Pythia mains), they're invisible. An injection
  grammar would light them up inside `string.quoted.double.cpp`.
- **No `language-configuration.json` for editor behaviour beyond comments.**
  Today's stub only sets the `!` line-comment. Pythia tolerates surrounding
  whitespace and continuation lines — minor, but worth a thought.

**Verdict.**
> Keep, expand. This is the only HEP-aware piece in the editor and it earns its
> place; the upgrade path is widening the grammar, not rewriting it.

### 1.2 `hep-contrast-theme` — audit

**What it does.** A light, high-contrast color theme generated by `theme.js`
(palette in JS → emits `themes/hep-contrast.json`). Tuned for C++ and Python with
extra rules for CMake, TOML, YAML, JSON, Markdown, Shell, and the `cmnd` scopes
from the sibling extension.

**Strengths.**
- The build script approach is correct — single source of truth, easy to refactor
  palette in one place.
- Semantic-token coverage is genuinely thoughtful: `selfParameter`, `clsParameter`,
  `variable.static`, `enumMember` all get their own treatment.
- Doxygen scopes are handled — non-trivial and useful for this project, which
  uses doc comments heavily in `utils/` and `modules/`.
- Bracket pair colors and peek/diff/debug surfaces are all wired through the
  palette, not hand-coded.
- Direct hooks for `cmnd` scopes — the two extensions already cooperate.

**Weaknesses.**
- **README palette table is stale.** Half the hex values listed don't match the
  palette in `theme.js`. (Fixed in this session, but worth a regression test:
  the README should be regenerated by `theme.js` too.)
- **No terminal ANSI palette.** README advertises "Full 16-color ANSI terminal
  palette — calibrated for white background", but `theme.js` defines none of
  `terminal.ansiBlack/Red/Green/…/BrightWhite`. VS Code falls back to its
  default light-theme ANSI, which on this background is poorly calibrated
  (default `ansiYellow` is invisible on white).
- **Only a light variant.** A dark sibling is one palette flip away and would
  double the theme's reach without doubling maintenance, if the build script
  is parameterised.
- **Inconsistent palette comments.** `numbers: "#CC332A", // teal` — the color
  is red. Cosmetic, but it's the kind of thing that misleads the next editor.
- **No `terminal.tab.activeBorder` / no integrated-terminal contrast checks.**
  When the terminal panel is showing colored compiler output (clang errors,
  Pythia banner, ROOT prompt) it inherits these tokens.
- **Theme is light-only and white-bg-only.** README says background is white
  (`#FFFFFF`) but the palette uses `#F5F5F5` for `baseBackground` — `bgEditor`
  is white, side panels are gray. Worth documenting the layered model rather
  than calling it "white".
- **No `dark+` semantic fallback.** Users on a dark OS who briefly open the
  theme get blinded. Not the theme's fault, but a screenshot in the README
  would set expectations.

**Verdict.**
> Keep, refine. The bones are good. The work here is polish (fix the gaps the
> README already promised) plus a dark variant for parity.

## 2. What to expand, cut, change, improve

### 2.1 `cmnd-syntax`

**Expand.**
1. Add value-type subscopes:
   - `on` / `off` / `true` / `false` → `constant.language.boolean.cmnd`
   - integers and floats (including scientific) → `constant.numeric.cmnd`
   - particle IDs (`2212`, `-211`, …) — same as numeric, but consider a
     `constant.numeric.pdg.cmnd` so themes can highlight PDG codes specially
   - lists (`HardQCD:all = on, off`) — split into elements
2. Add `entity.name.section.cmnd` for the leading namespace segment so themes
   can give `Main:`, `Beams:`, `PDF:` a stronger weight.
3. Add a "disabled command" scope: `comment.line.exclamation.disabled.cmnd`
   triggered when the line after `!` matches the `Namespace:Key = …` pattern.
4. Add a TextMate injection so `.cmnd`-style strings inside C++ files (e.g.
   `pythia.readString("Beams:eCM = 13000.")`) light up. Scope target:
   `source.cpp string.quoted.double`.
5. Ship **snippets** for the 30-ish most common Pythia keys (beams, processes,
   PDF set, tune, random seed, number of events, output verbosity).
6. Consider a **hover provider** (TS-based, not pure grammar) that reads from a
   bundled `pythia-keys.json` and shows the Pythia manual blurb for each key on
   hover. This is the single highest-value upgrade for newcomers to Pythia.

**Cut.** Nothing. It's already minimal.

**Change.**
- Loosen the `=` regex to allow zero-or-more whitespace.
- Bump version to `0.1.0` once the type subscopes land — current `0.0.1` is
  honest, but the next change set is a real feature bump.

### 2.2 `hep-contrast-theme`

**Expand.**
1. **Define the full ANSI 16.** Pick values from the existing palette
   (`accentRedDark`, `gitAdded`, `accentBlue`, `accentWarn`, `namespaces`,
   `operators`, etc.) so the terminal panel is consistent with the editor.
2. **Dark sibling.** Parameterise `theme.js` with a `mode: "light" | "dark"`
   switch; emit `themes/hep-contrast-light.json` and `themes/hep-contrast-dark.json`.
   Most token rules can be shared; only `colors.*` and a few `fg/bg` swaps differ.
3. **Auto-generate the README palette table** from the palette object in
   `theme.js`, so the table can never drift again.
4. ROOT/Cling-aware tokens: when editing `.C` macros, support `R__LOAD_LIBRARY`,
   `gROOT`, `gStyle`, `gPad`, `gDirectory` as `support.variable.root` and give
   them the `namespaces` color.

**Cut.**
- The unused `fg4` slot (palette comment admits "unused in syntax now").
- Duplicated `diffAdded55` / `diffAddedText` — pick one.
- The Markdown italic/bold rules are very generic; consider letting VS Code's
  default rules handle them and only override the heading/link colors.

**Change.**
- Rename the build script to `build.js` (matches the README and the JSDoc
  comment at the top of the file) — or keep `theme.js` and fix the JSDoc.
  Either is fine; pick one and stop having the file lie about its name.
- Fix the `numbers: "#CC332A", // teal` comment (it's red).
- Document the layered background model in the README (`bgEditor = #FFFFFF`,
  `baseBackground = #F5F5F5`, sidebar/activity gray ramp).

## 3. New package proposals (ranked)

### P1 — **`hep-icons`** *(your proposal — detailed plan in §4)*
A file/folder icon theme derived from Material Icon Theme (MIT) with the
JS/web-framework noise stripped out and HEP + ML data icons added in.
**Why first:** highest visible payoff per hour. Every file in the explorer
benefits, every day.

### P2 — **`pythia-hover`** *(spin-out from §2.1 item 6)*
A small extension that bundles a JSON of every Pythia8 setting with its
default, type, and one-line description (scraped from the manual XML), and
serves hovers + auto-completion inside `.cmnd` files. Could later subsume
`cmnd-syntax`.
**Why:** the Pythia manual is *exactly* the kind of reference you currently
have to alt-tab to a browser for. A local hover collapses that loop.

### P3 — **`hep-snippets`** *(C++/ROOT/Pythia/Rivet)*
A snippets-only extension for the boilerplate you write over and over:
- Pythia: minimal `main()`, event loop, `pythia.next()` skeleton
- ROOT: `TFile`/`TTree`/`TH1` setup, `TCanvas` save, `RDataFrame` snippets
- Rivet: minimum analysis class skeleton
- HepMC: reader/writer skeleton
- Project-specific: `_Lambda_Reconstruction.cc`-style entry point

### P4 — **`hep-tasks`** *(VS Code tasks + launch configs)*
Ship a `tasks.json` and `launch.json` template that knows about this repo's
Makefile (`make Lambda_Reconstruction`, `make tests`, …) and ROOT's debugger
setup. Currently `.vscode/` has these locally; promoting a clean,
parameterised template into `editor/` lets new collaborators bootstrap.

### P5 — **`hep-statusbar`** *(stretch)*
Reads the active config TOML and shows in the status bar: `eCM=13TeV ·
nEvents=1000 · seed=99`. Cheap to build (one TextDocument parser, one
StatusBarItem), high signal during long sessions where you forget what the
config currently says.

### P6 — **`yoda-syntax`** *(stretch, only if you adopt Rivet)*
Highlighting for `.yoda` histogram files. Trivial grammar — but only worth
doing if Rivet enters your stack.

### P7 — **`fcl-syntax`** *(skip unless you join an experiment using ART)*
FHiCL is Fermilab's config language (LArSoft / NOvA / DUNE). Skip unless
relevant.

## 4. Icon theme — concrete plan

Source: `https://github.com/material-extensions/vscode-material-icon-theme`
(MIT, Philipp Kief). Audited: `src/core/icons/fileIcons.ts` (615 extension
mappings, 965 SVGs) and `src/core/icons/folderIcons.ts` (490 folder mappings).

### 4.1 Approach
Material is the right base:
- 1245 SVGs covering virtually every language and tool — a complete icon vocabulary
- One SVG per icon, plus `_light` and `_open` variants — consistent grid
- MIT license; you can fork, prune, extend, redistribute

**Extension strategy (not a replacement).**
The theme is not a pruned fork — it is MIT with HEP additions layered on top.
Every icon MIT provides is preserved. HEP-specific types get their own custom
SVGs; everything else falls through to MIT's existing vocabulary.

Implementation: `build.js` reads MIT's installed `dist/material-icons.json`,
re-roots all icon paths from `dist/`-relative to extension-root-relative
(`./icons/`), then merges in the HEP `iconDefinitions` and extension/folder
name entries. The final `hep-icons.json` is fully self-contained.

```
editor/hep-icons/
├── package.json
├── build.js          # merge MIT JSON + HEP additions → hep-icons.json
├── hep-icons.json    # generated (do not edit directly)
└── icons/
    ├── [MIT SVGs — 1245 files with hash suffix, verbatim from MIT install]
    └── [HEP SVGs — 13 custom, no hash suffix, authored in editor/icon-bank/]
```

**Build steps.**
1. `node build.js` — auto-detects latest installed MIT in `~/.vscode/extensions/`,
   merges, writes `hep-icons.json`.
2. `vsce package --no-dependencies` — produces `hep-icons-X.vsix`.
3. `code --install-extension hep-icons-X.vsix`.

**Note on `.C` (ROOT macros, macOS).** On macOS VS Code extension matching
is case-sensitive, so `.C` does *not* automatically use the `c` icon. You
must explicitly add `'C'` to the `fileExtensions` list for either `c` or a
new `root-macro` icon. Recommend: add `'C'` to the `cpp` extensions list
(it's C++ in practice in `root_macros/`) and move on; a dedicated
`root-macro` icon is precious and you can always add it later.

## 6. Open questions / decisions to make

- **Publish or local-only?** All current extensions have `"publisher": "local"`.
  If you plan to share with collaborators, register a publisher ID on the VS
  Code marketplace; otherwise sticking with `.vsix` distribution is fine.
- **One mega-extension or many?** Right now each concern is its own extension.
  That's the right call for the icon theme (independent activation) and theme,
  but `cmnd-syntax`, `pythia-hover`, `hep-snippets` could merge into a single
  `pythia-tools` extension to reduce install friction. Recommend: merge those
  three.
- **OS theme integration.** If you ever want light/dark to follow the system,
  ship both `hep-contrast-light` and `hep-contrast-dark` in the same
  extension so VS Code's auto-switch picks them up as a pair.
